# ADR-0024: OIDC logout: RP-initiated and back-channel

**Status:** accepted (2026-11-09)

## Context

ADR-0019 added OpenID Connect login and left logout local: signing out of Superhet kept the user's session at the identity provider alive (the next "Sign in with ..." logs in without a prompt), and signing out at the provider (or an admin ending the session there) left Superhet sessions running until they expired. For a shared SDR with a role per user that is the wrong way round: single sign-on users expect single sign-out. Two standard mechanisms cover it: OpenID Connect RP-Initiated Logout 1.0 (Superhet tells the provider) and OpenID Connect Back-Channel Logout 1.0 (the provider tells Superhet). Front-channel logout (the provider loads our URL in an iframe) is not considered: it needs third-party cookies, which browsers are removing.

## Decision

1. **RP-initiated logout, only where it makes sense.** `POST /api/v1/auth/logout` ends the local session as before. If that session came from OIDC (see 3), OIDC is on, the admin switch `rp_logout` (default on) is on, discovery shows the same issuer the session was created with, and the provider's discovery document has an `end_session_endpoint`, the reply is 200 `{"end_session_url"}` instead of 204 and the web UI navigates the browser there. The URL carries `id_token_hint` (the stored ID token, omitted if none), `client_id`, `post_logout_redirect_uri` (`<public URL>/`, to be registered at the provider) and a random `state`, appended to whatever query the endpoint already has. The local session is deleted first and unconditionally: a provider that is down or slow (discovery gets a 4 s budget) costs the redirect, never the sign-out. The `state` is not checked on return: the landing page is the public login page and nothing happens with it. Password sessions, OIDC sessions of a provider without the endpoint, and sessions of an issuer that has since changed get the old 204.
2. **Back-channel logout endpoint.** `POST /api/v1/auth/oidc/backchannel-logout` (public, form-encoded `logout_token`, switch `backchannel_logout`, default on) validates the token following section 2.6 of the specification: signature against the provider's key set from discovery (asymmetric algorithms only; `none` and HMAC are refused; the keys are re-fetched once when the `kid` is unknown or the signature fails, like for ID tokens), `iss` equal to the discovered issuer, `aud` containing our client id, `iat` within five minutes (one minute of clock skew), `exp` if present not passed, `events` containing the `http://schemas.openid.net/event/backchannel-logout` member as an object, `sub` or `sid` present, **no `nonce`**, `jti` present and not seen before. `typ` is not required (Keycloak sends `Logout`, others `JWT`); the events/nonce rules are what keep an ID token from being accepted. `exp` is optional because early drafts and several implementations omit it; `iat` bounds the age either way. Signature verification uses the JWK implementation of the `openidconnect` crate (no new dependency); only the JWT envelope and claim checks are written here, as pure functions with a test per rejection.
3. **Sessions remember where they came from.** Migration 0014 adds `oidc_issuer`, `oidc_sid` (the ID token's `sid`) and `oidc_id_token` to `sessions`. Rows of password logins keep them null. The ID token is stored because it is the `id_token_hint` and the provider needs it to know which session to end without asking the user; it is signed, short-lived, and goes away with the session row (logout, expiry, revocation). Tokens above 16 KiB are not stored (the hint is then left out). It never leaves the server except in the end-session redirect to the provider that issued it.
4. **Matching.** `sid` ends the sessions of that issuer with that provider session id; `sub` alone ends all OIDC sessions of the account linked to that `(issuer, sub)`; both together must both match. Only sessions with an `oidc_issuer` are touched, so a user's password sessions survive, and a provider can never end sessions of another issuer. Unknown sessions are not an error (200): the user may already have signed out here. The ended sessions' open WebSockets are closed as for an admin revocation. `jti` values are remembered in memory until no token with them could pass the age check; an entry is released again if ending the sessions failed, so the provider's retry works. A restart empties the set, which only matters for a token replayed within the five minute window, and replaying a logout is idempotent anyway.
5. **Abuse handling.** The endpoint is unauthenticated by nature. It has its own failure limiter (20 refused requests per address and 200 in total per five minutes), deliberately not the password-login limiter, so a misconfigured or hostile caller cannot lock people out of password sign-in. Bodies are capped at 16 KiB, tokens at 12 KiB. Refusals answer 400 with a stable reason code and are audited coalesced; accepted logouts are audited individually.
6. **Settings and audit.** `rp_logout` and `backchannel_logout` are part of the `oidc` settings document and of the environment form (`SUPERHET_OIDC_RP_LOGOUT`, `SUPERHET_OIDC_BACKCHANNEL_LOGOUT`). The admin page shows the two URLs to register at the provider and the connection test reports whether the provider advertises an end session endpoint. Audit: `auth.logout` gains `provider_logout`; `auth.oidc_backchannel_logout` records issuer, `sid`, `sub`, the number of ended sessions, or the refusal reason.
7. **Provider-specific behaviour is documented, not special-cased.** `docs/oidc-providers.md` has hand-run recipes for Authentik and Keycloak. They were written from the providers' documentation and are not verified against running instances in this repository's tests, which use the mock provider only.

## Consequences

- Sign-out at either side now propagates (given the provider supports it and is configured with the two URLs); without that configuration nothing changes for the user, apart from the browser visiting the provider's end-session page on sign-out.
- The provider needs to reach `<public URL>/api/v1/auth/oidc/backchannel-logout` from its network. Behind a reverse proxy the path must be forwarded like the rest of `/api`; no cookies or Origin are involved.
- Providers that do not put `sid` into ID tokens can only log out by `sub`, which ends every OIDC session of that user at once.
- Groups and roles still follow the provider only at login (ADR-0019); a back-channel logout ends sessions, it does not re-evaluate roles.
- Stored ID tokens add up to a few KiB per OIDC session; they are removed with the session.
- Front-channel logout and the `logout_hint` parameter are not implemented.
