# ADR-0006: Database

**Status:** accepted (2026-10-20)

## Context

Data: settings, profiles, bookmarks, plugin registry, users/sessions, lookup cache, self-learned TETRA cells/subscribers, and a large, write-heavy event log (POCSAG, ADS-B, AIS, TETRA signalling – millions of rows per month) with full-text search, field filters and timeline queries. Several services (api, worker, pluginhost) access the data concurrently. Recordings and IQ are files.

## Options

1. **SQLite** (WAL, FTS5): zero-config, but single-writer, file shared between containers, weak for concurrent multi-service access and large analytic queries.
2. **PostgreSQL**: real concurrent multi-client server, declarative partitioning, `tsvector` + GIN full-text search, `pg_trgm` for fuzzy callsign/ID search, JSONB for event payloads, mature backup tooling, LISTEN/NOTIFY.
3. PostgreSQL + TimescaleDB: hypertables and compression for time series; extra extension, parts under the Timescale License.

## Decision

**PostgreSQL (current major, pinned image) as the only database**, accessed via `sqlx` (compile-time checked queries, embedded migrations in `superhet-db`). Schema `superhet`. Event log: table partitioned by month (declarative partitioning, partitions created/dropped by the worker), payload as JSONB, generated `tsvector` column with GIN index, `pg_trgm` index on source/destination identifiers. ADS-B/AIS position updates are aggregated before storage. TimescaleDB is not used now; native partitioning covers the requirements without an extra license.

Only the worker writes events (batched `COPY`/multi-row inserts from a JetStream consumer); api reads; each service has its own DB role with minimal privileges.

## Consequences

- One more container in compose; credentials generated by `scripts/gen-secrets.sh`, never committed.
- CI runs integration tests against a real PostgreSQL service container.
- Backups: `pg_dump` script + documented restore in `deploy/`; retention configurable (default 180 days events).
